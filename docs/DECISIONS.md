# 意思決定ログ

この文書には、後から理由を失うと困る長期的な判断だけを記録する。細かな実装判断はPull Requestやコードへ残し、ここには増やしすぎない。

## 2026-09-16 — CIは文書専用変更を軽量化する

**決定**

Pull Request / `main` pushの変更ファイルを最初に分類し、`docs/` 配下とリポジトリ直下のMarkdownだけが変更された場合は、変更分類jobだけを実行してフルCIを省略する。

それ以外のファイルが1つでも含まれる場合、または差分を安全に判定できない場合は、従来どおりcheck / test / build / sitemap / security / performance / browser smoke / SEO validationをすべて実行する。

文書判定は `docs/**` とリポジトリ直下の `*.md` に限定する。将来 `src/` 等にbuild入力となるMarkdownが追加されても、自動的にdocs-only扱いしない。

**理由**

プロセス標準化の文書変更PRでも、依存installから3種類のbrowser smokeまでフル実行しており、変更リスクに対して過剰だった。`project-planning-template` の「変更内容に必要な検証だけを選ぶ」方針に合わせ、品質gateを緩めずにCI時間と無駄な実行を減らすため。

**代替案・補足**

workflow自体を `paths-ignore` で起動しない方式は採用しない。CI workflowは常に起動し、軽量な変更分類jobを成功させた上で重いjobだけをskipする。これにより、将来required checkを設定する場合も「CIが全く作られない」状態を避けやすくする。

外部のchanged-files Actionは追加せず、checkout済みGit履歴の差分だけで保守的に判定する。

## 2026-09-16 — project-planning-templateの開発プロセスを採用する

**決定**

EOL情報.jpの企画・開発・検証・公開後改善は `slothwright/project-planning-template` の考え方を標準プロセスとして採用する。

プロジェクト側では、企画の基準点を `docs/PROJECT.md`、重要な判断を `docs/DECISIONS.md`、現在地を `docs/CURRENT_STATE.md` に分離する。中期の順序は既存 `ROADMAP.md`、専門的な恒常手順・設計は既存の専用文書を維持する。

判断権限は `PROCEED / INFORM / ASK`、実装後の判断は `PASS / FIX / REVISE / STOP`、公開後の判断は `CONTINUE / OPTIMIZE / REVISE / STOP / 未判定` を基本とする。

**理由**

現在のEOL情報.jpは実装・CI・運用基盤は十分に強い一方、企画目的、重要判断、現在地が `README.md`、`ROADMAP.md`、`PROJECT_HANDOFF.md`、チャットに分散していた。長期的な情報源をリポジトリに統一し、新しいチャットやAIでも判断理由から復元できる状態にするため。

**代替案・補足**

テンプレート内のすべての文書をコピーしない。必要な専門文書は既に存在するため、文書量を増やすこと自体を目的にしない。

## 2026-09-12 — 1年後のプロダクト像を「検索入口 + 継続監視」とする

**決定**

1年後の目標を「EOLを調べるならまずここを見る。重要な製品はそのまま監視できる、日本語のEOL管理サイト」とする。

基本導線は `検索で発見 -> 情報を信頼 -> 判断 -> マイEOLへ登録 -> 必要なら通知 -> 再訪` とする。

**理由**

既存実装には検索向け公開ページと、マイEOL・通知・GitHub Import等の継続利用機能の両方がある。どちらか一方を先に捨てるより、検索を入口にして実利用データから主軸を判断できる構成が最も既存資産と低コスト方針に合うため。

## 2026-09-12 — 成長施策は実データで3〜5ページずつ行う

**決定**

Search Consoleの主要URLのインデックス状態とQueries / Pagesが比較可能になるまで、大規模なSEO変更を行わない。

Phase 7開始後は、表示回数、CTR、掲載順位、検索意図との不足を根拠に改善対象を3〜5ページへ絞る。改善は原則1仮説ずつ行い、28日程度観測し、データ不足なら56日程度まで延長する。

結果は `win / neutral / lose / insufficient data` を基本に整理し、成功パターンだけを横展開する。

**理由**

立ち上げ直後の検索データが少ない時期に全ページへ推測変更を広げると、効果の原因を追えず、保守負担も増えるため。

## 2026-09-12 — 月次KPIは既存計測を優先する

**決定**

月次では原則として直近28日とその前の28日を比較し、Search、Usage、Trust、Operationsの4層を確認する。

主な指標は次のとおり。

- Search: impressions、clicks、CTR、average position、index状況、上位Queries / Pages
- Usage: Cloudflare Web AnalyticsのPage Viewsと主要ページの閲覧傾向
- Trust: snapshot freshness、手動レビュー鮮度
- Operations: CI、browser smoke、sitemap、SEO、security、performanceの未解決異常

現時点ではマイEOL追加等の専用イベント計測を新設しない。検索から継続利用への接続を判断する必要性が具体化した時点で、匿名・最小限・低コストの計測を再検討する。

**理由**

計測基盤そのものを先回りして増やさず、既存のSearch ConsoleとCloudflareでまず需要を確認するため。

## 2026-09-12 — 製品コンテンツをTier A / B / Cで扱う

**決定**

- Tier A: 検索・閲覧需要が大きく、独自情報追加の価値が高い。積極的に改善する
- Tier B: 一定需要がある。必要十分な独自情報を維持する
- Tier C: ロングテール。正確なEOLデータベースとして維持する

所属製品は事前固定せず、実データで決める。コンテンツ量には差を付けても、データ正確性は全Tierで同じ水準を求める。

**理由**

全製品を同じ密度で手作業更新すると、利用価値に対して保守負担が大きくなるため。

## 2026-09-12 — 3〜6か月後に主軸を実利用から選ぶ

**決定**

Baseline取得後およそ3か月で、検索中心・管理ツール中心・信頼性DB中心のどこに強い兆候があるかをレビューする。半年時点では各方向を `Primary / Secondary / Maintenance` に分類し、開発配分を見直す。

作った機能だからという理由だけで追加投資しない。2回以上改善しても効果が確認できない、56日経っても判断に必要なデータが得られない、運用負荷が価値に見合わない等の場合は、その施策の優先度を下げる。

**理由**

現在の最大の不確実性は実装可能性ではなく、利用者が検索・監視・信頼性確認のどこに最も価値を感じるかだから。

## 2026-09-12 — 開発配分はGrowth gate前後で変える

**決定**

Growth gate中は、保守・信頼性40%、実利用から見つかったUX改善30%、文書・計測準備・技術的負債30%を目安とする。

Phase 7開始後は、保守・信頼性20%、UX改善15%、文書・技術的負債10%、データ駆動改善50%、新規実験5%を目安とする。

この比率は厳密な工数表ではなく、1〜2か月単位で偏りを防ぐ判断材料とする。本番障害や品質gate失敗は比率より優先する。

**理由**

Search Console待ちで推測SEOを増やさず、Phase 7開始後も成長施策だけに偏って運用品質を落とさないため。

## 2026-09-12 — 収益化は信頼・中立性を損なわない範囲で後から判断する

**決定**

収益化は目的ではなく継続運営の手段とする。需要・利用者像が数回の公開後レビューで見えてから検討する。

スポンサーによる掲載順位変更、通常コンテンツに見せかけた広告、閲覧・マイEOL情報の販売、過度なトラッキング、基本EOL情報の有料壁化は行わない。

候補はスポンサー、実需要のある法人向け利便機能、必要になった場合の商用APIを優先し、一般的なディスプレイ広告は最後に検討する。

**理由**

EOL情報サイトでは正確性と中立性がプロダクト価値の中心であり、短期収益でそれを損なうと差別化そのものを失うため。

## 2026-09-12 — 編集品質は一次情報・事実と解釈の分離を優先する

**決定**

EOL情報.jpは「公式情報をもとに、ソフトウェアのEOL・サポート期限を日本語で判断しやすく整理するサイト」と位置付ける。

公式一次情報を優先し、事実とサイト側の解釈を区別する。不明な日付を推測しない。AIは下書き・比較補助・校正に利用できるが、公式ソース確認なしでEOL日・サポート条件・移行情報を確定しない。SEO目的の大量AI生成ページは作らない。

**理由**

情報量より正確性・根拠・更新可能性を優先することが、単純なデータ転載との差別化と長期的な信頼につながるため。

## 2026-09-10 — Search Console反映待ちをGrowth gateとする

**決定**

主要URLのインデックス状態、Queries / Pagesの比較可能な実データ、sitemap / canonical / noindexの技術的正常性が確認できるまで、Phase 7の検索成長施策を待つ。

固定日数が経過したことだけを開始条件にしない。

**理由**

クロール済み・未登録の状態で推測変更を繰り返すより、技術異常の有無と実際の検索需要を分けて判断する方が検証可能だから。
