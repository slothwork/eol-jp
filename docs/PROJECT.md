# プロジェクト概要

最終更新: 2026-09-16

この文書は、EOL情報.jpの目的・提供価値・優先順位・主要制約を確認するための基準点です。短期の現在地は `docs/CURRENT_STATE.md`、重要な判断理由は `docs/DECISIONS.md`、中期の実行順序は `ROADMAP.md` を参照します。

## 企画概要

ソフトウェア・OS・データベース・フレームワーク等のEOL（End of Life）とサポート期限を、日本語で判断しやすく整理し、必要な製品は継続監視までつなげられるサイトを提供する。

## 目的

1年後の目標状態は次のとおりとする。

> EOLを調べるならまずここを見る。重要な製品はそのまま監視できる、日本語のEOL管理サイト。

基本導線は `検索で発見 -> 情報を信頼 -> 判断 -> マイEOLへ登録 -> 必要なら通知 -> 再訪` とする。

PVや機能数の最大化は目的にしない。検索から正確な情報へ到達し、必要に応じて継続監視へ進めることを価値とする。

## 想定ユーザー

主対象は日本の次の利用者。

- ソフトウェア開発者
- インフラ / SRE / プラットフォーム担当
- 情シス / 社内IT担当
- 複数の製品・バージョンのサポート期限を把握する必要がある担当者

個人利用から小規模な企業利用までを主対象とし、現時点では重い組織管理・アカウント基盤を前提にしない。

## 提供価値

- 製品・バージョンのEOLとサポート期限を日本語で素早く確認できる
- 公式一次情報と出典をたどれる
- 「あと何日」や期限区分により、対応の優先度を判断しやすい
- 変更履歴・監査情報・公式ソース照合により、根拠と更新経緯を確認できる
- マイEOL、リマインダー、通知、GitHub Importにより、検索して終わらず継続監視へ進める

## 優先順位

判断に迷う場合は、原則として次の順で優先する。

1. 正確性・信頼性
2. 主要なEOL確認体験の分かりやすさ
3. 実データで確認できた利用価値
4. 表示速度・安定性・低運用負荷
5. 機能数や見栄え上の拡張

本番障害、品質gateの失敗、データ鮮度の異常は、通常の新機能より優先する。

## 重要な制約

- 継続運用コストはほぼ0円を維持する
- 公開コンテンツはAstroの静的生成を基本とする
- 本番buildではlive endoflife.date APIへ依存せず、コミット済みsnapshotを利用する
- ブラウザ内で完結できる個人状態は可能な限りlocalStorageで扱う
- アカウント、恒久DB、private GitHub認証などは明確な需要と再設計判断なしに導入しない
- 有料サービスや新しい外部依存は、必要性・費用・障害時挙動・データ保存範囲を確認してから採用する
- Google検索だけに依存した成長判断をしない
- Search Consoleの実データが不足している間に、推測だけでSEO変更を繰り返さない

## 市場・競合に関する現在の結論

新規企画時の詳細な事前調査を後付けで捏造しない。この文書では、現在のプロダクト判断に必要な結論だけを保持する。

主な代替手段は、endoflife.date、各ベンダーの公式ライフサイクル文書、検索エンジン、社内台帳・スプレッドシート等である。

EOL情報.jpは単なるendoflife.dateの日本語表示ではなく、次の組み合わせで差別化する。

- 日本語での判断しやすさ
- 公式ソース照合と変更監査
- 日本向け商用サポート等の補助情報
- 検索からマイEOL・通知までの継続監視導線

この差別化仮説は、Search Console・閲覧実績・実利用のデータで継続的に再評価する。

## やる価値

EOLは検索時点の確認だけでなく、移行計画・更新判断・社内管理へ継続的に関係するため、正確な検索入口と軽量な監視機能を一体化する価値がある。

既存の静的データ基盤、公式ソースレビュー、監査ログ、通知、マイEOL、GitHub Importを組み合わせることで、検索サイトと管理ツールの両方を低コストで検証できる。

## 収益化の見込み

収益化はサイトの目的ではなく、継続運営を支える手段とする。正確性・中立性・閲覧性・プライバシーを損なう収益化は行わない。

現時点では収益化を急がず、少なくとも数回の公開後レビューを行い、継続的な需要と主な利用者像が見えてから判断する。

候補の優先順位は次のとおり。

1. 明確に区別されたスポンサー / サポーター
2. 実需要が確認できた場合の法人向け便利機能
3. API利用量やサポート要求が増えた場合の商用枠
4. 一般的なディスプレイ広告は最後に検討

EOL日、サポート期限、製品ページ、公式ソース、基本的な検索・一覧は無料公開を維持する方針とする。

## SEO・集客可能性

SEOは重要な入口だが、最終目的ではない。

主要検索意図は `{product} EOL`、`{product} サポート期限`、`{product} {version} EOL` 等。検索流入後に、正確な情報確認、公式ソース確認、マイEOLや通知などの次の行動へつながることを重視する。

Search ConsoleのQueries / PagesとCloudflare Web Analyticsを主な既存データ源とし、需要のある3〜5ページずつ改善する。全製品を一律にSEO最適化しない。

## 差別化方針

- 正確・分かりやすい・根拠が追えることを優先する
- 「最も詳しい」より「EOLについて迷ったとき安心して確認できる」を先に成立させる
- 公式一次情報とサイト側の解釈を区別する
- 実需要が大きい製品だけ独自情報を厚くする
- 検索して終わりではなく、継続監視へ自然につなげる

## デザイン・UX方針

- 比較・一覧が主目的の画面は高密度テーブルを基本とする
- 探索・説明・確認操作が主目的の箇所はカードを使う
- ISO日付だけでなく残日数と状態を併記する
- モバイルでも期限と状態を読みやすくする
- localStorageや外部API等が失敗しても、基本的なEOL情報の閲覧を妨げない
- デザイン定義・表示・ドメインロジックを、保守価値がある範囲で分離する

## 編集・コンテンツ品質方針

情報源は原則として次の順で重視する。

1. ベンダー / 公式プロジェクト
2. endoflife.date
3. 日本法人等の国内公式情報
4. 公式GitHub Repository / Release
5. 二次情報

事実と解釈を分け、不明な日付は推測しない。AIは下書き・比較補助・校正には利用できるが、公式ソースを確認せずEOL日・サポート条件・移行情報を確定しない。SEO目的の大量AI生成ページは作らない。

コンテンツ量は需要に応じてTier A / B / Cで差を付けても、データ正確性は全Tierで同じ水準を求める。

## 実現性と難易度

現在の主要機能は実装済みで、Phase 0〜6の公開・運用・テスト基盤まで成立している。今後の主要な不確実性は技術実現性より、検索需要と継続利用のどちらが強いかというプロダクト上の方向性にある。

そのため、当面は新しい大型基盤より、本番データを使った小規模な検証を優先する。

## 運用コスト方針

継続的な運用コストは原則0円を目標とし、Cloudflare・GitHub Actions・静的配信・ブラウザローカル処理など既存の無料構成を優先する。

通知等で既に動的基盤が必要な箇所を除き、新しいWorker / KV / DB / 外部サービスを先回りして追加しない。

## 主要リスク

- Googleのインデックス・検索流入が想定より伸びない
- 検索流入はあってもマイEOL等の継続利用につながらない
- 全製品を同じ密度で手動整備し、保守負荷が高くなる
- 公式情報とupstreamデータの差異を誤って確定扱いする
- 機能追加によって低コスト・プライバシー重視の強みを失う
- 文書・CI・運用管理が実開発より重くなる

## GO判断の理由

公開済みプロジェクトのため新規企画時のGO判断を再現しない。現時点では、主要機能・運用基盤が成立しており、検索需要と継続利用のどちらに寄せるべきかを実データで検証できる段階にあるため、継続改善を `CONTINUE` とする。

## 非目標

需要が確認されるまでは次を行わない。

- バージョン専用indexable URLの大量生成
- 全製品への手作業による大規模コンテンツ拡充
- GitHub Importのmonorepo / private repository等への先回り拡張
- ユーザーアカウントや恒久DBの導入
- private GitHub認証
- 有料解析サービスの導入
- 高度な法人管理機能の先行開発
